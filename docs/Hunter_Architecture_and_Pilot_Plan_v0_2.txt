3  Omo brain: decisions without execution
READ → collect reproducible facts and current candidate context. THINK → generate a provisional thesis, competing hypothesis, catalyst, invalidation trigger and questions to resolve. GATE → deterministic checks for source provenance, freshness, identity confidence, risky contract mechanics and budget eligibility. JOURNAL → persist a versioned decision with evidence and exact known-at timestamp. REVISIT → update after a meaningful state change and evaluate previous hypotheses.
Brain output
Semantics for a personal read-only Hunter
ALERT_NOW
Dispatch first wallet-discovery alert even when thesis not ready; say “unverified”.
DEEP_RESEARCH
Schedule bounded origin, holder, market-structure and narrative research.
WATCH / RECHECK
Persist triggers such as holder change, creator acknowledgment, liquidity move or source update.
CONTRADICTION
Correct or downgrade a prior claim; keep original decision and correction audit trail.
DEPRIORITIZE
Stop spending AI credits on this candidate; never discard original wallet event.
INSUFFICIENT_EVIDENCE
Keep uncertainties visible; do not fill gaps with imagined facts.
Omo’s original public code has separate market read, AI-thesis, audit/gate and pipeline modules (omotrades/omo). Adapt the conceptual decision loop, not the trading execution code; do not import privileged wallet, signing, swap or transaction-commitment modules.
4  Intelligence quality: observe everything, conclude carefully
A strong Hunter keeps three distinct outputs: (A) research priority; (B) structural/manipulation risk; and (C) evidence confidence. None should override the others. The first alert contains observed facts; deeper reports contain model interpretations explicitly labeled as hypotheses.
Token originality: compare prior mints with normalized names/tickers, metadata URIs, image fingerprints, deployer history and timestamped public source chronology. “Earliest found in covered datasets” is not proof of first-ever or official creator affiliation.
Holder lifecycle: resolve token-account owners, concentrate on net changes, top-holder movements, funding paths, buyer dwell times, liquidity-pool vs externally owned accounts and multi-wallet interactions.
Fake-volume / MEV / bot factors: spot opposing-leg churn, buy-volume-to-holder-growth divergence, repeated counterparties, same-slot activity, priority fee/tip context, wash-like patterns and common-funder evidence. Preserve confidence and alternative explanations; these are not decisive flags or proof of a named actor.
Narratives: independently check primary creator posts, original meme evidence, token socials and any promised future updates. Unavailable X/TikTok/Instagram evidence remains UNKNOWN, not FALSE.
Early warning: compare current token behavior to matched age, liquidity and launchpad cohorts; use falsifiable windows (15m, 1h, 24h), not guaranteed breakout forecasts.
Surprise engine: allow bounded, scheduled anomaly/hypothesis generation from stored on-chain evidence; send only verified, material discoveries to the user; save unsuccessful hypotheses too.
5  Permanent memory and control plane
Use one Aiven Postgres schema, not a new graph or vector database. Core entities: watched_wallet, onchain_event, token, token_metadata_version, holder_snapshot, relation_edge, source_document, evidence_claim, investigation_job, decision_version, prediction, outcome, alert, vendor_usage and operator_state.
A decision keeps: token mint, discovered source wallet(s), blockchain event signatures, normalized observations, evidence IDs, alternate hypotheses, contradiction list, timestamp known-at, reviewer result, model/rule versions, spend and next recheck trigger. Append; never silently overwrite historical judgments.
Operator modes: FULL (free-capped research), WATCH_ONLY (ingest + non-AI alert), PAUSE_RESEARCH (save queued events but no new AI), STOP_ALL (disable new event handling and jobs as far as provider controls permit). STOP_ALL does not automatically cancel fixed vendor subscriptions; manual billing controls remain important.
Resilience: unique (signature, instruction path, event kind) IDs; retries with bounded dead-letter status; confirmed/finalized reconciliation; source lag and last-success monitoring; daily cheap DB export and restore test. The 1 GB Aiven Free storage cap requires retention and aggregation rules: raw payloads are not kept indefinitely.

9  Budget policy and upgrade triggers
Pilot target: $0 incremental infrastructure if all existing accounts remain within free-tier quotas; engineering time is not included. No credit card or paid subscription should be enabled automatically. Separate any fixed Render/Aiven account fees already being paid from newly incurred application costs.
Upgrade only after collecting real metrics. Worker CPU errors → paid Cloudflare Workers (published starting around $5/month). Render Free sleeps → switch UI to static assets or pay for always-on compute. DB 1 GB/storage or connection pressure → higher Aiven tier. Helius missed-event/credit depletion → adjust filters, then evaluate paid data. AI quota exhausted → pause full reasoning and keep watch-only facts. Purchase broader social access only after proving it changes decisions.
The first upgrade purchase is optional, not scheduled automatically after day five. A hard controller checks daily and monthly request caps before each paid call, refuses new paid work at the limit and keeps the operator audit log. Third-party overages can still occur if vendor billing and local metering disagree; use vendor-side spending safeguards as available.
